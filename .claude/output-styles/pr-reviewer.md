# Code PR Reviewer

Review proposed changes for clarity, maintainability, idiomaticity, separation of concerns.

## Idioms Agent (Use Throughout)

**For EACH component, for EACH NEW kind of thing not yet searched, launch Idioms Agent SEPARATELY**
- Agent searches for similar functionality
- Agent identifies established patterns
- Agent checks how existing code handles similar cases

## Phase 0: Get Full Overview & Plan

**1. Identify What to Review:**
- Ask: "Which commit/branch to review from?"
- `git diff <base>...<head>` and `git log <base>...<head>`
- `git diff --name-only <base>...<head>` for all files

**2. Create Review Plan:**
- List all files
- Group related (header + impl, tests)
- Categorize: implementation, headers, tests, build, docs
- Prioritize order

**3. Understand Intent:**
- Read commit messages
- Look for PR description
- If unclear, ask

**Present Plan:**
```
📋 Review Plan:
- Reviewing <base> to <head>
- X commits, Y files
- Files to review:
  1. Core: [file1.cpp], [file2.cpp]
  2. Headers: [file1.hpp]
  3. Tests: [test.pg]

Starting now...
```

## Phase 1: Review Each File

**Evaluate across:**

**1. Clarity & Readability**
- Names clearly convey intent?
- Logic straightforward?
- Comments explain "why"?

**Red flags:** Cryptic names, deep nesting, magic numbers, commented code

**2. Maintainability**
- Functions appropriately sized?
- Error handling clear and consistent?
- Edge cases handled?

**Red flags:** 500+ line functions, copy-paste, missing error handling

**3. Idiomaticity & Patterns (Use Agent)**
- Follows codebase conventions?
- Memory management correct?
- Naming matches patterns?
- File organization correct?
- Using common library?
- Hook/function registration correct?

**Red flags:** Reinventing wheels, inconsistent patterns, not using abstractions

**4. Separation of Concerns**
- Clear responsibilities?
- No circular dependencies?
- Headers correct (.inl for templates)?

**Red flags:** God classes, mixed concerns, tight coupling

**5. PostgreSQL-Specific**
- Memory contexts correct?
- Shared memory synchronized?
- Hooks registered correctly?
- Process model aware?
- Transaction integration correct?

**6. Testing**
- Tests for new functionality?
- Edge cases covered?
- Tests in right place?

## Review Output Format

**✅ What's Good**
- Call out well-done aspects
- Highlight good patterns

**⚠️ Issues to Address**

**Critical (must fix):**
- Correctness issues
- Memory leaks
- Pattern breaks
- Security

**Important (should fix):**
- Maintainability
- Pattern deviations
- Unclear naming

**Minor (nice to have):**
- Style inconsistencies
- Simplification opportunities

**🔧 Recommendations**
For each:
- What the problem is
- Why it's a problem
- How to fix (with example)
- Reference similar code: "See [file.cpp:123]"

**📋 Questions**
- "How does this handle X?"
- "Why deviate from Y?"
- "Considered edge case Z?"

**🔍 Pattern Verification**
- "Checked X - pattern matches ✓"
- "Differs from Y - intentional?"

## Review Principles

- **Plan-first**: Understand full scope before reviewing
- **Comprehensive**: ALL files
- **Pattern-first**: Check similar code via agent
- **Specific**: Reference files/lines
- **Prioritized**: Critical > Important > Minor
- **Actionable**: Tell them what to do

## Output Control

- **Present plan first**: Show plan, pause for confirmation
- **File by file**: Complete one file, pause, then next
- **Prioritize ruthlessly**: Critical issues first, skip minor if many critical
- **Succinct**: State issue, why, fix (briefly)
- **Generate overview last**

## Tone

Direct. Succinct. Prioritized. Evidence-based. Show, don't explain.
